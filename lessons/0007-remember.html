Always-On Agents · Lesson 07

Remember

The model forgets everything. Memory is files the harness reads, writes, and chooses to show.

Time: 45 min Build: profile + logs Stack: Python + DeepSeek Map: memory

Lesson 02 kept the execution state across a crash. That is not the same as remembering you. The journal knows which tool ran; memory knows who you are, what you decided last week, and what the agent already tried.

The model still has no memory. Every request is a fresh read of whatever the harness chose to send. So "memory" is two things: files on disk, and a harness that decides which parts of them enter the chat.

The one idea

Storage is not context. The agent can keep years of notes, but the model only sees the few lines the harness puts in the prompt. Memory is a selection problem, not a storage problem.

1. Three layers, three costs

The talk layers memory by the cost of including it, not by topic. [talk §05]

  • Core facts. Who you are, how you want to be spoken to. In every prompt, so they must stay short.
  • Dated logs. What happened on a given day. Searched when a question needs them.
  • Scratchpad. Notes for the current task. Ephemeral; thrown away when the task ends.
  • Files, skills, memories. The long tail. Kept on disk and retrieved on demand.

Our build implements the first two and the retrieval path. The profile is read by the harness and appended to the system prompt. The logs are written by the harness after each turn and searched by a recall tool.

Why not load all logs? They grow without bound. A year of notes would crowd out the task. Search is how the agent gets the past without paying for all of it.

2. Build it

The server gains three things: a profile block in the system prompt, a remember tool that appends facts, and a recall tool that searches dated logs.

Build step · ~25 minutes

2 terminals
  1. Seed a profile and one log from yesterday.
  2. Ask what it remembers. Then teach it a new fact.
  3. Restart the server and ask again. The fact survives the process.
# terminal A $rm -rf build/lesson-03/state build/lesson-03/memory $.venv/bin/python build/lesson-07/seed.py $.venv/bin/python build/lesson-03/server.py
# terminal B $.venv/bin/python build/lesson-03/client.py "What do you remember about me?" $.venv/bin/python build/lesson-03/client.py "Remember that I prefer bullet points over paragraphs." $.venv/bin/python build/lesson-03/client.py "What did we work on in the log analysis?"

The first answer should include the seeded profile facts. The second should call remember; the fact is appended to build/lesson-03/memory/profile.md. The third should call recall and quote yesterday's log.

Now restart the server in terminal A — Ctrl-C, then run it again — and ask the same first question. The new fact is still there, because the harness reads the profile at startup. The model never stored it.

# build/lesson-03/memory/profile.md
# Profile
- Works on a personal always-on agent in Python.
- Prefers short, direct explanations.
- Timezone: Africa/Nairobi.
- Prefers bullet points over paragraphs.

Look at the server log. You should see recall {"query": ...} and remember {"fact": ...} as ordinary tool calls. That is the whole memory system: two tools and a file the harness reads.

3. What this costs

Profile tokens are paid every turn. Every fact in the profile sits at the front of the prompt and is sent on every request. It is also part of the cached prefix, so adding a fact invalidates the cache once — acceptable for a rare write, expensive if you write facts constantly.

Recall is a search, not understanding. It matches lines. If the question needs synthesis across dates, the model has to search several times.

Facts can be wrong, stale, or poisoned. A fact learned from an email or a webhook can be an injection. Memory needs attribution, review for sensitive facts, and a way to delete. None of that is in this build.

The talk's discipline is garbage collection: decide which facts deserve the always-on cost, and let the rest live in files. [talk §05] Anthropic calls the file version structured note-taking, and it is the same idea: persist outside the window, pull back only what the task needs.1

What this build does not do

No dedupe, no conflict resolution, no deletion, no review, no per-user isolation. The profile is a flat file that any turn can append to. Do not put secrets in it, and do not let untrusted events write to it.

Retrieval check

Where do core facts about the user go?

Why: core facts shape every reply, so they must be present every time. That is also why they must stay few and short.

What does the recall tool do?

Why: the logs stay on disk. The search brings back a few lines, and only when the model asks.

What is the cost of a fact in the profile?

Why: the profile is part of the prefix. Every fact is a permanent tax on every turn, and a cache break when it changes.

What you can now do

  • Separate storage from context, and say which memory layer pays which cost.
  • Teach the agent a fact and prove it survives a server restart.
  • Search dated logs through a tool instead of loading them.
  • Name the memory risks: staleness, poisoning, and missing deletion.
