Always-On Agents · Lesson 01

The loop that dies

An agent is a model calling tools in a loop. That loop is easy. Keeping it alive when the process ends is the whole course.

Time: 45 min Build: one file Stack: Python 3.12 Map: reference

Your mission is a colleague in the cloud that keeps working after you close the laptop. Before anything can survive a crash, you need to see exactly what crashes. It is smaller than it looks — and the failure is more interesting than you expect.

The one idea

An agent is not a model. It is a model plus a harness that executes tools and owns the conversation. The model never runs anything; it asks. Everything in the talk — memory, triggers, sub-agents, its own computer — is built on this boundary.

1. A turn is three steps, repeated

Each round trip has the same shape. You send messages and a list of tool schemas. The model replies with either text or one or more tool calls — a name and a JSON argument blob. Your code executes them, appends the results, and calls the model again. When a reply contains no tool calls, the turn is over.

That is the entire mechanism. Anthropic's description is blunt: agents "are typically just LLMs using tools based on environmental feedback in a loop."1 The 12-Factor Agents guide writes it as four lines of pseudocode: determine the next step, execute it, append the result, repeat until done.

Why the boundary matters. The model can ask to run rm -rf. The harness decides whether it runs. Treat every tool name and argument as untrusted input, not as a command from you.

Two details in that loop will matter for the rest of the course. First, the result is the model's only evidence that anything happened. Second, the messages list is execution state: it holds the pending tool call, the history, and the step count. Where that list lives determines whether your agent survives anything.

Retrieval check

The model returns a tool call. What does the harness do next?

Why: the appended result is the model's only evidence for the next decision. Ending the turn first would make multi-step work impossible.

2. Build the smallest honest loop

The build is deliberately framework-free. You should be able to point at every line that turns a chat completion into an agent. Later lessons can use a framework because you will know what it is hiding.

Build step · ~25 minutes

3 commands
  1. Open build/lesson-01/agent.py. Find the three parts: TOOLS (schemas the model sees), execute() (the only code that touches the world), and run() (the loop).
  2. Run a two-tool task. Watch one API call per round.
  3. Read the saved transcript and match each message to a step in the diagram.

Run these from the repo root. The $ is the shell prompt — start typing after it, not at it. No activation needed: .venv/bin/python is the interpreter.

$.venv/bin/python build/lesson-01/agent.py "Create hello.md with the line 'Hello from the loop'. Then read it back and confirm."

You should see something close to this — the exact tool choices vary between runs:

[1] write_file {"path": "hello.md", ...}
    -> wrote 21 chars to hello.md
[2] run_shell {"command": "cat hello.md"}
    -> exit code: 0
       Hello from the loop.

I created hello.md, then read it back to confirm the contents.

Count the calls. Two tool rounds means three model calls: one to choose each tool, and one to write the summary. Cost scales with rounds, not with the size of the task description.

The only clever line in the file is the stop condition: if not message.tool_calls. There is no planner, no graph, no framework. The model decides; the harness executes.

One caveat: run_shell runs on your machine, confined only to a workspace directory. That is convenient, not safe. Lesson 8 replaces it with a disposable VM; until then, do not give this toy anything you would not give a stranger.

3. Now kill it

Here is the experiment that the rest of the course exists to fix. Reset, then run a task that writes a file, and pull the power right after write_file returns — after the side effect, before the result is recorded.

Predict before you run

When the process dies mid-turn, what is in workspace/plan.md? What is in state/transcript.json? Write your answer down before running — being wrong here is the lesson.

Reveal

The file exists, with content. The transcript stops at the last completed step, so the agent has no record of the write, and no idea the file changed. On resume it redoes the step: it may overwrite the file, or inspect it and validate it instead. It cannot simply continue.

$rm -rf build/lesson-01/state build/lesson-01/workspace $.venv/bin/python build/lesson-01/agent.py "Create plan.md with exactly three bullets about launching a small agent. Then read it back and count them." --crash-on write_file # the write lands on disk, then the process dies before recording the result $cat build/lesson-01/workspace/plan.md $cat build/lesson-01/state/transcript.json

Then resume, and compare the file before and after:

$cp build/lesson-01/workspace/plan.md /tmp/plan-before.md $.venv/bin/python build/lesson-01/agent.py "Create plan.md with exactly three bullets about launching a small agent. Then read it back and count them." --resume $diff /tmp/plan-before.md build/lesson-01/workspace/plan.md

A clean diff is still a result: it means the agent rediscovered its own work through the filesystem, which is not the same as remembering it. A dirty diff is the more dangerous outcome — the same step produced a different world the second time.

What you should notice:

  • The side effect survived the crash. The knowledge of it did not.
  • The transcript is valid, but it describes a world that no longer matches the filesystem.
  • Resume replays the lost step — overwriting, or re-checking, depending on the run. For a file that is survivable; for an email or a payment it is not.
  • What saved the resumed run was the file itself. The filesystem is a checkpoint your harness did not have to write — and a hint of why so much agent memory ends up in files.

This is not a bug in the toy. Replace os._exit with a deploy, an out-of-memory kill, or a dropped connection. The same gap appears, just less politely.

4. Name what you saw

Two kinds of state were in that process. Business state is the work itself: the file, the record, the side effect. Execution state is where the run had got to: the pending call, the messages, the step count. The 12-Factor Agents guide's Factor 5 is exactly this: unify them, or at least make sure they cannot silently disagree.2

The talk's fix is not "save more often". It is a different execution model. A job queue, after a crash, replays steps one, two, three. A durable workflow journals what it is about to do and what happened, so a retry resumes at step three. The talk uses Temporal for this, runs the loop on the server, and keeps the computer separate so the VM can be rebuilt without killing the run.3

Your checkpoint saves after a result. A real journal records the decision before executing it, so replay can see "I already called write_file with this content" and choose not to repeat it. That difference — before versus after — is the next lesson's problem, and the reason the agent can run for days.

Retrieval check

A process dies just after a tool has run. What actually survives?

Why: the filesystem has no idea your process died. Only the in-memory transcript is lost — which is precisely why it is dangerous: the record and the world disagree.

What does a durable workflow change about a retry?

Why: progress is journaled, so the retry has a place to continue from. A queue without a journal only knows how to start over.

Why does the talk run the agent loop on a server, apart from the VM?

Why: the talk's stated reason: if the loop lived inside the VM, you could not rebuild the VM without dropping the run. Separating them is what makes a zero-day patch a non-event.

What you can now do

  • Explain to another engineer why an agent is a harness, not a model.
  • Read a transcript and say which step produced each message.
  • Show, with a running process, the gap between an execution state and the world.
  • Distinguish a queue replay from a workflow resume — and say why the second one lets an agent run for days.
