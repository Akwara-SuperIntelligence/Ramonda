The always-on agent, on one page

A compass for the course. Every box here is one lesson. Read this to see where you are; read the lessons to learn how to build the box.

Source: the talk, §01–§06 Use for: orientation, design review Print: yes, one page-ish

1. The shape: thin client, thick server

Everything the agent can do lives on a server. The client — terminal, phone, Slack, email — only carries messages. In the talk's harness, exactly one tool crosses that boundary: send_user.1 The client receives it and decides how to render it richly: a sign-in form, a payment sheet, an approval card, or just an emoji reaction.

That single boundary is why a new client costs days instead of months. It is also why the agent loop can be upgraded, scaled, and restarted without shipping an app.

2. Waking up

An always-on agent is mostly asleep. That is a feature: keeping a VM and a process warm for every user is expensive and does not scale. [talk §03] On a trigger, the server loads the user's state, boots the computer only if the task needs it, works, then puts both back to sleep and persists.

The router in front of the loop does three jobs: dedupe (one event, one run), priority (your direct message preempts a background routine), and batch (three quick messages become one turn). [talk §03]

3. Surviving the crash

The loop itself is trivial. What is not trivial is that a run can last hours or days, across deploys and failures. A job queue replays from step one after a crash; a durable workflow journals each step and resumes at the failed one. [talk §03] The talk uses Temporal for this and runs the loop on the server, separately from the VM, so the computer can be rebuilt without dropping the run.

Job queueDurable workflow
After a crashReplays step 1, 2, 3…Resumes at the step that failed
Side effectsMay repeatJournaled, so replay can be made safe
Good forIndependent short jobsA single long, stateful run

Definition and mechanics: Temporal, durable execution. The state-design principle is 12-Factor Agents, Factor 5.

4. Remembering

Memory is layered by cost of inclusion, not by topic. [talk §05]

LayerWhat lives thereWhen it is read
Core factsWho you are, how you like to be spoken toEvery single prompt
Dated logsWhat happened on a given daySearched when relevant
ScratchpadEphemeral notes for the current taskThis hour, then discarded
Files, skills, memoriesEverything else — the long tailOn demand, by shell and search

The last row is why the agent has a computer. Files give it unbounded memory with cheap retrieval: it can grep, head, and read only what it needs. Anthropic, context engineering

5. Staying lean

Context is a finite attention budget, and every turn of a long conversation spends it. [talk §05] The talk's levers, in order of payoff:

  • Keep the prefix static. System prompt and tool schemas never change mid-conversation, so prompt caching keeps working. A cache miss is a bug.
  • Hash and order prompt sections. An A/B test must not reshuffle everyone else's prefix.
  • Show tool names, load schemas on demand. "Dynamic tool discovery" keeps dozens of connectors from eating the window.
  • Put long output in a file. Return a path instead of a 40,000-token blob.
  • Delegate expensive work to a sub-agent. It burns its own fresh context and returns a summary.
  • Compact inside the warm cache window. Summarising while the cache is hot is cheaper than after it expires.

6. Acting on the world

Try the cheapest, most reliable rung first; only then bother the user. [talk §04]

  1. What the model already knows from the conversation.
  2. A plugin, MCP server, or API.
  3. Web search.
  4. The browser on its own machine.
  5. The whole desktop: scripts, apps, files.
  6. The user — for input or approval.

Inside the browser, the same ladder applies: the accessibility tree is cheaper than the HTML, which is cheaper than a screenshot, which is cheaper than clicking pixels. Fall back down the rungs only when the higher one fails. [talk §04]

7. Not being annoying

Not every event deserves a message. The talk's heuristic: send a status update roughly once a day, or when something genuinely needs the user — not on every increment of progress. [talk §03] This is a product policy, not a model capability, and it belongs in the harness.

8. Being trusted

Three separate problems, often conflated:

  • Command review. A second model reviews shell commands before they run — "auto-review". At enough scale this beats human approval fatigue. [talk §04]
  • Prompt injection. Untrusted input (email, webhook, web page) must never be treated as an instruction from the user. [talk §04]
  • Irreversible actions. Sending, paying, deleting: draft, ask, then act. Keep passwords out of the conversation entirely. [talk §04]

9. Getting better

Two loops. The inner loop is days: a failure becomes an eval, the harness or prompt is fixed, the eval proves it. The outer loop is months: new models are trained on harness traces and climb the same evals. [talk §06] The teams that win are the ones whose evals encode what they actually care about.

Where this course is going

Each lesson adds one box to the map. Later lessons are written as you get there — this list is a plan, not a promise.

  1. The loop that dies — build the three-step loop; kill it; name what was lost. Lesson 01
  2. Write it down before you do it — journal the intent before the call; reconcile on restart. Lesson 02
  3. The process is not the agent — move the loop to a server; one send_user boundary. Lesson 03
  4. Wake on events — triggers, router, priority, batching, silence. Lesson 04
  5. Stay lean — prompt caching, compaction, tool search, files over context. Current lesson
  6. Delegate — sub-agents with fresh context, orchestrator and helpers.
  7. Remember — profile, logs, scratchpad, skills as files.
  8. Give it a computer — sandbox VM, browser, accessibility tree.
  9. Trust it — auto-review, injection, approvals, secrets.
  10. Get better — evals, the inner and outer loops.
