At scale, comparing your query against 10 million vectors one by one would take forever. So, under the hood, data stores like Pinecone, Weaviate, or PGVector use an algorithm called Hierarchical Navigable Small World Graphs. It navigates a layered network to approximate your nearest neighbors instead of doing a full linear scan. Translation, you're trading a tiny fraction of perfect accuracy for massive speed. That's not a bug. That's the entire deal you're signing up for. And here's the limitation that bites everyone eventually. Embeddings are great at meaning, but terrible at exact tokens. Search for Stripe error code 402 and the vector search might confidently hand you five docs about generic payment failures, credit card declines, and webhook retry policies. Semantically, it matches the correct documents. But it has no idea that 402 is a magic string that it needs to match exactly. Same problem with acronyms, part numbers, product keys, or exact usernames. Semantic search fails miserably on exactly the stuff humans search for most. So, production systems don't pick just one. They run a hybrid search, dense vectors for meaning, and a classic keyword algorithm called BM25 for exact term matching. These are running side by side. Elasticsearch or OpenSearch natively support fusing both result sets together. It's giving your RAG system both a poet's intuition and a librarian's precision. And at scale, you genuinely need both halves of that brain. Now, relational databases, why do you still need boring old SQL sitting next to your fancy vector store? Two words, filtering and trust. Vectors are bad at hard constraints. Only HR documents, only docs that this user is allowed to see. Only this fiscal year. A relational DB does the filtering job instantly and also precise, narrowing 10 million candidates down to the few thousand. That way, semantic search never wastes a single cycle. There is one more trick that production systems rely on, re-ranking. Let's say that hybrid search hands you the top 100 candidates fast but rough. Then, a heavier model, a cross-encoder like Cohere's re-rank, actually reads the query together with each candidate and re-scores them properly. It's slower, so you only run it on 100, not 10 million. But it catches the subtle relevance gaps that pure vector math always misses. So, the rule of thumb is this, retrieval at scale is never one look up. It's a funnel. SQL filters out what you're not even allowed to see. Hybrid search finds what is probably relevant. Re-ranking decides what is relevant for real. Skip any one of those steps and your smart RAG system starts confidently returning garbage, but at least fast.
