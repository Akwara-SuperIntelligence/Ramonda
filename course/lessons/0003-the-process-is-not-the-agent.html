Always-On Agents · Lesson 03

The process is not the agent

Close the terminal. The loop should not notice. This lesson moves the model, the tools, and the history to a server, and leaves the client with one job: send text, show text.

Time: 45 min Build: server + client Stack: Python stdlib Map: the shape

Lessons 01 and 02 built a real agent: a loop, tools, a journal. But all of it lived in one Python process in one terminal. Close the terminal and the agent is gone. The journal survives on disk; nothing is left to read it and continue.

The talk's fix is older than agents: a thin client and a thick server. [talk §03–§04] The client sends a message and renders the reply. The server owns the model key, the tools, the files, the history, and the loop. One boundary, one payload shape.

The one idea

If the client disappears, the turn must still finish. That is the test of a real boundary. A client that holds the loop is not a client; it is the agent with a network cable.

1. What crosses the boundary

In the talk, exactly one tool crosses from server to client: send_user. The server decides what to say; the client decides how to show it — a form, a payment sheet, an approval card, an emoji. [talk §04]

Our build has the same shape in both directions: the client posts text, the server returns text. Everything else stays on the server.

Why move it? Server changes ship without an app update. Heavy tools run where the compute is. One server can serve many clients. And the client can be a phone that sleeps, a Slack tab that closes, or a terminal you Ctrl-C.

This is also the security boundary. The client never holds the model key, and never gets the tool schemas. A client that could call tools directly would be a second, unguarded harness.

2. Build it

The build is two small files. The server fits in one file. The client is about 40 lines, and contains no model, no key, no tools.

Build step · ~25 minutes

2 terminals
  1. Start the server in terminal A. Leave it running.
  2. Send a task from terminal B. Then send another and kill the client mid-turn.
  3. Read the history from a new client. The turn is there.
# terminal A — the only place with a key and tools $rm -rf build/lesson-03/state build/lesson-03/workspace $.venv/bin/python build/lesson-03/server.py # listening on http://127.0.0.1:8765

In terminal B, send a task that takes a few tool calls:

$.venv/bin/python build/lesson-03/client.py "Create numbers.md with the numbers 1 to 20, one per line. Then create total.md with the sum. Read both back and verify."

Watch terminal A. It prints each tool call as it runs. Terminal B prints only the final reply. That is the whole client.

Now the experiment. Send a second task, and press Ctrl-C in terminal B about two seconds after you press Enter:

$.venv/bin/python build/lesson-03/client.py "Create squares.md with the squares of 1 to 15, one per line. Then read it back and count the lines." # press Ctrl-C while terminal A is still working

The client dies. Terminal A keeps printing. When the turn finishes, the reply is saved to build/lesson-03/state/history.json, even though no client is listening. Start a new client and read it:

$.venv/bin/python build/lesson-03/client.py --history

You should see both turns: the one that completed normally, and the one whose client you killed. The file is in build/lesson-03/workspace.

Any client works. This is the same history through curl:

$curl -s http://127.0.0.1:8765/history | head -c 400

3. What you proved

The loop is not in the terminal. The terminal is a view. When the view died, the server finished the turn and saved the result. That is the difference between a chat program and an always-on agent.

The talk's server also holds the state that outlives the client: the conversation, the memories, the routines. The client is replaceable — mobile, desktop, Slack, email — because the boundary is one message. [talk §04]

What this build does not do

It has no authentication, so it binds to 127.0.0.1 only. It has no journal — the history file is not one, and a server crash can still lose an in-flight turn. And it wakes only when a client sends text. Each of those is a later lesson. Do not put this on a public port.

Retrieval check

Where do the model key, tools, and history live?

Why: the client only sends text and renders text. Everything that can act on the world stays on the server.

The client dies in the middle of a turn. What happens to the turn?

Why: the socket is not the work. The server thread keeps running, saves the transcript, and a later client can read it.

Why is the client allowed to be dumb?

Why: a client with no loop, no tools, and no key has nothing to protect and nothing to update. It can be replaced without touching the agent.

What you can now do

  • Draw the client/server boundary and say what crosses it.
  • Kill a client mid-turn and recover the result from the server.
  • Explain why keys, tools, and state never belong in the client.
  • Name the three things this build still lacks: auth, journal, triggers.
