Always-On Agents · Lesson 04

Wake on events

No one types. A schedule fires, a webhook arrives, and the agent starts. A trigger is just a client without a human.

Time: 45 min Build: router + trigger Stack: Python stdlib Map: waking up

Lesson 03 gave the agent a body on a server. But it still only worked when a client asked. That is a remote control, not a colleague. The talk's always-on agent has events on the left: a schedule, a Slack message, an email, a meeting. [talk §03]

This lesson adds the front door. A router receives events, drops duplicates, and wakes the agent server. No client is involved.

The one idea

A trigger is not a special path into the agent. It is a message that starts a turn. The router decides which messages become turns, and which are noise.

1. Triggers, router, server

Three jobs sit between the world and the loop. [talk §03]

  • Dedupe. One event, one turn. A webhook that retries three times must not start three runs.
  • Priority. Your direct message jumps ahead of a background routine. The talk's agents stop the current loop when you correct them.
  • Batch. Three quick messages become one turn, not three.

The router is also where the silence policy belongs. Not every event deserves a message. The talk's heuristic is roughly one status update a day, or when something genuinely needs you — not every increment of progress.

2. Build it

Two new files, three terminals. The agent server from lesson 03 does not change.

Build step · ~25 minutes

3 terminals
  1. Start the agent server (terminal A) and the router (terminal B).
  2. Fire an event from terminal C. No client is attached.
  3. Read the history. Then fire a duplicate and watch the router drop it.
# terminal A — the agent server from lesson 03 $rm -rf build/lesson-03/state build/lesson-03/workspace build/lesson-04/state $.venv/bin/python build/lesson-03/server.py # terminal B — the front door $.venv/bin/python build/lesson-04/router.py

In terminal C, send an event. There is no client:

$.venv/bin/python build/lesson-04/trigger.py "Check the workspace. If heartbeat.md is missing, create it with the current UTC time. Otherwise append one line with the current time. Use the date command."

The trigger prints accepted and exits. Terminal B prints the event, then the reply when the turn finishes. Terminal A shows the tool calls. Wait a few seconds, then read the history:

$.venv/bin/python build/lesson-03/client.py --history

Now send the same event id twice:

$.venv/bin/python build/lesson-04/trigger.py --replay "Append one line to replay.md with the word once."

Terminal B should show one [event] and one [duplicate]. The history gains one turn, not two. The router remembers the id in build/lesson-04/state/seen.json.

Finally, a schedule. This sends an event every 15 seconds until you stop it:

$.venv/bin/python build/lesson-04/trigger.py --every 15 "Append one line to log.md with the current time. Keep it short." # Ctrl-C after two or three events $.venv/bin/python build/lesson-03/client.py --history

Each event starts a turn. The agent works, writes, and goes back to sleep. Nobody typed.

This endpoint has no authentication

/event accepts any JSON from any local process. That is fine for 127.0.0.1. On a public port, it is a remote trigger for anyone. Auth and a tenant check are not in this build.

3. What you proved

The agent woke without a user message. The trigger was a client with no human, and the server did not care who called. That is the always-on part of always-on agent: events on the left, loop on the right.

You also proved why the router is separate. Dedupe is policy, not model work. The model never sees the duplicate; the router drops it before a turn starts. The same place will hold priority and batching when you need them.

4. What is still missing

  • Priority and batching. The router serialises turns; it does not preempt. A direct message waits behind a routine.
  • Notification. The agent cannot message you. You read history. The silence policy is a stub.
  • Auth. Localhost only. No tokens, no tenants.
  • Journal. This server still has lesson 03's plain history; lesson 02's journal is not wired in.

None of these is hard. Each is a lesson of its own. Do not add them all at once.

Retrieval check

What does the router do with a duplicate event id?

Why: dedupe happens before any turn starts. The model never sees the retry.

Why is a trigger described as a client without a human?

Why: the server only knows that text arrived. A human, a cron job, and a webhook look the same at the boundary.

What is still missing after this lesson?

Why: the agent can work, but it cannot reach you. You still have to poll the history. Notification is a separate path.

What you can now do

  • Draw triggers, router, and server, and say what each one decides.
  • Wake the agent with a schedule or webhook, with no client attached.
  • Drop a duplicate event before it becomes a turn.
  • Name the missing pieces: auth, priority, batching, notification.
