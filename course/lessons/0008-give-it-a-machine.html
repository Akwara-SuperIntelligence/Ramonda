Always-On Agents · Lesson 08

Give it a machine

The agent should not run on your laptop. This lesson moves its shell behind a machine interface — and shows why a directory is not yet a computer.

Time: 45 min Build: machine service Stack: Python stdlib Map: acting

Since lesson 03 the agent has run on your Mac. Its shell starts in a workspace directory, but it is still your machine: your files, your user, your network. The talk gives the agent a separate Linux box — its own files, browser, and desktop, snapshotted and rebuilt at will. [talk §03]

We cannot build Firecracker in an afternoon. We can build the interface a computer needs: run a command, reset it, snapshot it, restore it. Then the provider behind that interface can become a real VM without touching the agent loop.

Read this before the build

The box in this lesson is a directory with a service in front of it. It is not isolated. A command can still read the host. Do not run untrusted code in it. The interface is the lesson; the isolation is the next provider.

1. A machine as a service

The server keeps the loop, the model, and the tools. The machine keeps the files and the shell. The server talks to it over HTTP:

  • POST /run — run a command in the box.
  • POST /reset — delete everything in the box.
  • POST /snapshot — copy the box aside.
  • POST /restore — copy the snapshot back.
  • GET /tree — list the files.

The server's shell tool now calls /run instead of running locally. Set COMPUTER_URL and every main and helper command goes to the box. The loop does not know the difference.

2. Build it

Build step · ~25 minutes

3 terminals
  1. Start the machine, then the server pointed at it.
  2. Write a file and prove it lands in the box, not the server workspace.
  3. Reset, snapshot, restore — then try to escape the box.
# terminal A — the machine $rm -rf build/lesson-08/box build/lesson-08/snapshot build/lesson-03/state $.venv/bin/python build/lesson-08/computer.py # terminal B — the server, pointed at the machine $COMPUTER_URL=http://127.0.0.1:8767 .venv/bin/python build/lesson-03/server.py
# terminal C $.venv/bin/python build/lesson-03/client.py "Create hello.txt with the line 'hello from the box'. Then read it back."

Now check both sides:

$ls build/lesson-08/box hello.txt $ls build/lesson-03/workspace 2>/dev/null # nothing: the server never wrote the file

Reset the machine, with no snapshot yet:

$curl -s -X POST http://127.0.0.1:8767/reset $.venv/bin/python build/lesson-03/client.py "Read hello.txt and tell me what it says."

The box is empty and the agent reports the file missing. Recreate it, then snapshot, reset, and restore:

$.venv/bin/python build/lesson-03/client.py "Create hello.txt again with the same line." $curl -s -X POST http://127.0.0.1:8767/snapshot $curl -s -X POST http://127.0.0.1:8767/reset $curl -s -X POST http://127.0.0.1:8767/restore $.venv/bin/python build/lesson-03/client.py "Read hello.txt now."

The file is back. This is the lifecycle the talk describes: the machine can sleep, be rebuilt, and continue from a snapshot.

Now try to escape

Ask the agent what it can see outside its box:

$.venv/bin/python build/lesson-03/client.py "Run pwd and ls .. and report what you can see outside your box."

On the test run it answered:

"I'm in .../build/lesson-08/box, and one level up I see computer.py and snapshot/. This does confirm my shell isn't strictly confined."

That is the honest result. The box is a directory. The service does not isolate it. A real computer needs a kernel boundary, and that is what Firecracker provides.

3. What a real machine adds

A separate kernel and filesystem. The agent's commands cannot read your home directory, because there is no path to it.

Network policy. The box can be allowed to reach some hosts and blocked from others. A directory cannot enforce that.

VM-level snapshot. Firecracker snapshots memory and disk, then restores both. Copying a directory only preserves files; a running process and its memory are lost.

A browser and a desktop. The real box has Chrome. The agent can look at the accessibility tree, fall back to HTML, then to pixels. That is the retrieval ladder from the talk. [talk §04] It is not in this build.

The interface you just built is what makes those additions possible. The server sends a command and gets output. It does not care whether the box is a directory, a container, or a microVM.

What this build does not do

No isolation, no browser, no desktop, no network policy, no VM snapshot, no per-user boxes. Treat it as a mock of the machine interface, not a sandbox. The next provider is Firecracker or a managed sandbox service.

Retrieval check

Why is this box not a real computer?

Why: the service is a wrapper around a directory on your host. The escape test proves it: the shell can read the parent.

What must the server change to use a real VM?

Why: the server sends commands to a service. Swap the provider, keep the loop. That is the value of the interface.

What does a VM snapshot preserve?

Why: Firecracker captures memory and disk. Our /snapshot copies files only; a running process would not survive.

What you can now do

  • Route the agent's shell through a machine service.
  • Reset, snapshot, and restore the machine without touching the loop.
  • Demonstrate why a directory is not isolation, and name what a VM adds.
  • Explain why the interface survives a change of provider.
