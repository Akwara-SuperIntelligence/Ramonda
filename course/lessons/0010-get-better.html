Always-On Agents · Lesson 10

Get better

A change is not an improvement until a test says so. Turn every failure into a case, and run the cases on every change.

Time: 45 min Build: eval suite Stack: Python Map: getting better

Nine lessons built an agent that runs, survives, wakes, remembers, delegates, has a machine, and reviews itself. How do you know a change made it better rather than different?

The talk has two loops. The inner loop is daily: a failure becomes an eval, you fix the harness or the prompt, the eval proves it, you ship. The outer loop is monthly: the failures become training data, and a new model climbs the same evals. [talk §06] This lesson builds the inner loop.

The one idea

An eval is a test, not a vibe. It sets up a state, runs the agent, and checks the artifact. If it can pass while the agent is broken, it is not an eval.

1. The flywheel

Every production failure should leave a case behind. The case is small, deterministic, and cheap. It fails before the fix and passes after. It stays in the suite, so the same failure cannot return silently.

2. Build the suite

Five cases: two for the reviewer, three for the agent. Each starts from a clean box, runs, and checks the artifact or the verdict. The script exits 1 if anything fails, so CI can use it.

Build step · ~20 minutes

3 terminals

  3. Break one expectation on purpose, rerun, and watch it go red.

Each case is a function with three parts: a task, an action, and a check. The check is ordinary Python:

def numbers() -> None:
    ask("Create numbers.txt with the numbers 1 to 5, one per line.")
    text = (BOX / "numbers.txt").read_text()
    lines = [line.strip() for line in text.splitlines() if line.strip()]
    assert lines == ["1", "2", "3", "4", "5"], f"got {lines}"

No model grades this. The filesystem is the judge.

Now break it. Open build/lesson-10/evals.py, change "hello from eval" in the check to "hello from evals", and run again. One case goes red, the exit code becomes 1, and the message shows what it got. Change it back. That is the whole loop: a red test is information, not a setback.

What to put in the suite

  • Core tasks. The things the product must do: create a file, answer from memory, finish a multi-step task.
  • Security cases. The reviewer denies rm -rf, an injection does not delete the inbox, an irreversible tool needs approval.
  • Regressions. Every production failure becomes one case, with the exact input that broke it.

3. What to measure, and what to avoid

Measure: pass rate, time per case, tokens per case, and the number of tool calls. The suite already prints time; add tokens by reading the server log or the history. Cost is part of quality.

Avoid grading with the same model that generated the answer. It is circular and it drifts. Use deterministic checks when the artifact can be checked. Use a different model, or a human, only for qualities that cannot be asserted.

Avoid a suite that never changes. It becomes a museum. Add a case for each real failure; retire cases that no longer reflect the product. The set should encode what you care about now.

The talk's outer loop depends on this: you cannot train on failures you never recorded, and you cannot tell whether a new model is better without a stable set of cases. [talk §06]

What this suite does not do

Five cases is a start, not coverage. There is no CI, no token accounting, no flake detection, no holdout set, and no human review. It runs against one model. Treat it as the shape, not the finished thing.

Retrieval check

What makes a good eval check?

Why: a check that a broken agent can still pass teaches nothing. Assert on the file, the state, or the verdict.

What is the inner loop?

Why: the inner loop is the daily engineering loop. Training is the outer loop, and it uses the same cases.

Why keep evals after the model improves?

Why: a better model can still break your harness, your prompts, or a case that used to pass. Evals are how you notice.

What you can now do

  • Write an eval as a setup, an action, and a deterministic check.
  • Run a suite that exits non-zero, so CI can gate a change.
  • Turn a production failure into a permanent case.
  • Say what the inner and outer loops share, and why the suite must grow.
