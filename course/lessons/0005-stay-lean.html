Always-On Agents · Lesson 05

Stay lean

Long context is not more intelligence. It is a larger bill and weaker recall. Most tokens should be cached, and most content should not be in the context at all.

Time: 45 min Build: measure the cache Stack: Python + DeepSeek Map: staying lean

The agent now runs for days. Every turn resends the conversation. Left alone, the context grows until it is expensive, slow, and worse at recall. The talk calls the discipline context engineering, and treats a cache miss as a bug. [talk §05]

The one idea

The context is an attention budget, not a storage bin. Pay for the smallest set of tokens that produces the right behaviour, and keep the prefix stable so most of it is cached.

1. The attention budget

Models lose accuracy as the context grows — the "context rot" effect. Attention pairs every token with every other token, so the attention work grows with n², and the model's ability to find the right detail drops. Anthropic's guidance is blunt: find the smallest set of high-signal tokens.1

Four levers do most of the work. This lesson measures the first and explains the rest; sub-agents get their own lesson.

  1. Static prefix + prompt caching. Keep the system prompt and tool schemas byte-identical between calls, so the provider can reuse its cached computation.
  2. Tool search. Send tool names only; load a schema when the model asks for it. Dozens of MCP connectors otherwise eat the window before the task starts.
  3. Files over context. A long tool output goes to a file; the context gets the path. The agent reads what it needs with head, grep, or a query.
  4. Compaction. Near the limit, summarise the conversation and continue from the summary. Lossy by definition; the algorithm decides what survives.

2. Measure the cache

The build is one small script. It sends the same long prefix three times, then sends it with a changing timestamp at the front. DeepSeek reports cache hits in usage, so the difference is visible in tokens.

Build step · ~20 minutes

1 command
  1. Run the meter. Read the hit and miss columns.
  2. Run it again. The first call may already hit — the cache persists for hours.
  3. Find the line in the script that changes the prefix, and say why it destroys every later token.
$.venv/bin/python build/lesson-05/meter.py

Your numbers will differ with the model and the day. The pattern should not:

model: deepseek-chat
prefix chars: 18600

stable 1   prompt= 3613  hit=    0  miss= 3613
stable 2   prompt= 3613  hit= 3456  miss=  157
stable 3   prompt= 3613  hit= 3456  miss=  157
unstable 1 prompt= 3625  hit=    0  miss= 3625
unstable 2 prompt= 3625  hit=    0  miss= 3625
unstable 3 prompt= 3625  hit=    0  miss= 3625

Stable prefix: after the first call, 96% of the input came from the cache. Unstable prefix: zero, every time. The only difference is one line at the front.

Best effort, not a guarantee. DeepSeek builds the cache in seconds and clears it after hours or days. Hits depend on exact prefix units. Measure your own traffic; do not assume.

The provider's documentation is precise: a cache hit needs a prefix that fully matches a cached prefix unit. DeepSeek persists units at request boundaries and fixed intervals, and exposes prompt_cache_hit_tokens and prompt_cache_miss_tokens so you can see the result.2

3. The other levers

Tool search

Every tool schema is tokens the model must read before it does any work. With one connector it is nothing; with twelve MCP servers it is most of the window. Dynamic tool discovery sends names first and loads the schema on demand. [talk §04] The trade is one extra round trip for a much smaller baseline.

Files over context

A command can return 40,000 tokens. You almost never need them all. Write the output to a file and return the path and a short tail. The agent can grep the file, read the lines around a match, or run a query. This is the practical reason the agent has its own computer: storage is cheap, attention is not.

Compaction

Eventually the conversation exceeds the window. Compaction summarises it and starts fresh with the summary plus the few files that matter. Anthropic's implementation preserves architectural decisions, unresolved bugs, and implementation details, and discards redundant tool output.1 It is lossy. The art is choosing what survives.

The talk adds a timing trick: compact while the cache is still warm. Summarising a long conversation is itself a model call; doing it before the cache expires is cheaper. [talk §05]

Order, hashing, and pre-warming

Keep prompt sections in a fixed order, and hash each section so an A/B test cannot reshuffle the prefix for everyone else. Pre-warm the cache when the user opens the chat, the way a web page prefetches a link. [talk §05]

What this does not buy

Caching cuts cost and latency, not context rot. Compaction loses details. Tool search costs a turn. Files need retrieval discipline. None of these is free; each is a trade you measure.

Retrieval check

Which change breaks the cache for every later token?

Why: the cache matches a prefix. A new suffix keeps the old prefix intact; a new first line replaces it.

What should happen to a long tool output?

Why: the path is cheap and the file is durable. The agent can read the part it needs, when it needs it.

What does compaction lose?

Why: compression discards information. The algorithm decides which details survive, and it will sometimes be wrong.

Why keep the prompt prefix static?

Why: exact reuse is the condition for a hit. A static order also lets you hash sections and test changes without collateral damage.

What you can now do

  • Read cache hit and miss tokens, and explain what a miss costs.
  • Find the token in a prompt that invalidates the prefix.
  • Choose between context, a file, and a summary for a large output.
  • Say what compaction loses, and why the timing of it matters.
