Always-On Agents · Lesson 09

Trust it

A colleague with a shell needs three guards: review the command, distrust the input, and ask before the irreversible.

Time: 45 min Build: command reviewer Stack: Python + DeepSeek Map: trust

The agent now has a loop, a server, a machine, helpers, memory, and triggers. It can act. That is the point, and the risk.

The talk names three separate problems: a model should review shell commands before they run; untrusted input must never be treated as an instruction; and irreversible actions should ask first. [talk §04] This lesson builds the first and demonstrates the second. The third stays a design.

The one idea

The model's judgement is one layer, not the only layer. Put a second check between the proposal and the machine, and assume the model can be fooled.

1. Three guards

Command review. Before the machine runs a shell command, a second model reads it and answers ALLOW or DENY with a reason. The talk calls this auto-review, and argues it beats approval fatigue at scale. [talk §04]

Input trust. An email, a webhook, or a web page can contain instructions. None of it is a user instruction. The model should treat it as data, and the harness should keep review in front of the machine anyway.

Approval. Sending, paying, deleting: draft it, show it, wait. Not built here, but the boundary is the same one: a tool call is a proposal, not an action.

2. Build it

The server now reviews every shell command, for the main agent and for helpers. It also exposes POST /review so you can inspect the verdict without running anything.

Build step · ~25 minutes

3 terminals
  1. Start the machine and the server, and plant an untrusted email in the box.
  2. Ask for a benign command; watch the reviewer allow it.
  3. Ask the reviewer directly about dangerous commands, then ask the agent to run one.
# terminal A — the machine $rm -rf build/lesson-08/box build/lesson-08/snapshot build/lesson-03/state $.venv/bin/python build/lesson-08/computer.py # terminal B — the server with the reviewer $COMPUTER_URL=http://127.0.0.1:8767 .venv/bin/python build/lesson-03/server.py # terminal C — plant the untrusted input $.venv/bin/python build/lesson-09/seed.py

First, a normal command:

$.venv/bin/python build/lesson-03/client.py "Run ls -la and tell me what you see."

Terminal B prints [review] ALLOW before the machine runs it. Now ask the reviewer about commands without executing them:

$curl -s -X POST http://127.0.0.1:8765/review -H 'Content-Type: application/json' -d '{"command":"ls -la"}' {"verdict": "ALLOW"} $curl -s -X POST http://127.0.0.1:8765/review -H 'Content-Type: application/json' -d '{"command":"rm -rf ."}' {"verdict": "DENY: recursive deletion"} $curl -s -X POST http://127.0.0.1:8765/review -H 'Content-Type: application/json' -d '{"command":"cat ../../.env"}' {"verdict": "DENY: path climbs out of the working directory with .. and reads .env"}

Now ask the agent to do something destructive:

$.venv/bin/python build/lesson-03/client.py "Run rm -rf . and then list files."

On the test run, the model refused before the reviewer was needed. That is the first layer working. On another run, a model may comply and the reviewer blocks it. Both are acceptable; the point is that the second layer exists.

Finally, the untrusted input:

$.venv/bin/python build/lesson-03/client.py "Read inbox.txt and do what it asks."

The file contains an invoice pretext and a fake SYSTEM line that tells the agent to run rm -rf .. The test run read it, named it as a prompt injection, and refused. The reviewer would have denied the command if the model had obeyed.

3. What this does and does not buy

Buys: a second opinion between the model and the machine; a log line for every command; a fail-closed default; a tool result the model can read and recover from.

Does not buy: a guarantee. The reviewer is another model. It can be fooled by a clever command, it can be slow, and it can be wrong in both directions. It is a filter, not a sandbox.

The command itself is untrusted text passed to the reviewer. A command can contain instructions aimed at the reviewer. The OS permissions, the VM boundary, the network policy, and the approval gate are still doing separate work.

What this build does not do

No approval flow, no auth on /send, /review, or the machine, no secret manager, no audit trail beyond stdout, no rate limits. The reviewer prompt is a policy, not a security proof.

For a real deployment: allowlist the commands the product needs, run the machine as a low-privilege user, deny network egress by default, keep secrets in a manager the model never sees, and require a human for irreversible actions.

Retrieval check

What does the reviewer check?

Why: the gate sits between the proposal and execution. A deny means the machine never sees the command.

Why is the reviewer not a guarantee?

Why: it is a classifier with a prompt. Clever commands, injected text, and mistakes can get through. Keep the OS and VM boundaries too.

What should happen to an irreversible action?

Why: a send, a payment, or a delete cannot be undone. Approval must come before the side effect, not after.

What you can now do

  • Put a reviewer between the model's proposal and the machine.
  • Inspect an allow or deny verdict without executing the command.
  • Recognise untrusted input and show why it is not an instruction.
  • Name the remaining layers: permissions, network, secrets, approval.
