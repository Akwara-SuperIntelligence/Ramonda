Always-On Agents · Lesson 06

Delegate

The main conversation should stay small. Give the expensive work to a helper with fresh context; take back only the report.

Time: 45 min Build: helper loop Stack: Python + DeepSeek Map: context

Lesson 05 kept the context lean with caching, files, and compaction. But some work is simply expensive: scanning a large file, trying ten commands, reading twenty pages. If the main agent does that, its context fills with tool output it will never need again.

The talk's answer is a helper: a sub-agent with its own fresh working memory. The main agent hands over a focused task, the helper burns its own context, and only a short report comes back. [talk §02, §04]

The one idea

The helper's tool calls are not the main agent's context. Delegation is context isolation, not just parallelism.

1. A second loop

A helper is not a new kind of model call. It is the same agent loop with a different system prompt, a fresh message list, and a narrower tool set. It cannot see the main conversation, so the brief must be self-contained.

Anthropic describes the pattern the same way: specialised sub-agents work in clean context windows, explore with tens of thousands of tokens, and return a condensed summary. The lead agent keeps the plan and synthesises.1

Helpers are not free. They add latency, duplicate work, and can misread the brief. Use one when the task is big enough that isolation pays for the extra call.

The talk goes further: each helper is its own durable workflow, so a failed helper can restart without losing the main run. [talk §04] Our build leaves that out for now; the helper is a plain loop.

2. Build it

We add one tool to the lesson 03 server: delegate. The main loop is unchanged. The helper is a second loop with its own message list and only the shell tool.

Build step · ~25 minutes

2 terminals
  1. Seed a 6,000-line log in the workspace.
  2. Start the server and give it the analysis task, with instructions to delegate.
  3. Read the server log: the [helper] line and the [main] line.
# terminal A $rm -rf build/lesson-03/state build/lesson-03/workspace $.venv/bin/python build/lesson-06/seed.py $.venv/bin/python build/lesson-03/server.py
# terminal B $.venv/bin/python build/lesson-03/client.py "In workspace/big.log, count the lines for each level (INFO, WARN, ERROR) and find the three most frequent ERROR messages. Delegate the analysis to a helper. Then verify the helper's report and write report.md with the counts and the top three errors."

The server log is the lesson. On the test run:

[1] delegate {"task": "In your workspace there is a file ..."}
  [helper] 8 tool calls, 21090 tokens
[2] run_shell {"command": "cd workspace; ..."}
[3] run_shell {"command": "cat > report.md ..."}
[main] 12 messages, ~2778 tokens

The helper spent 8 tool calls and about 21,000 tokens. The main conversation ended at 12 messages and roughly 2,800 tokens. The main agent never saw the helper's tool results — only its report, and then re-ran the counts itself to verify.

Your numbers will differ. The shape is what matters: a large helper context, a small main context, one report between them.

Check the artifact:

3. What this buys, and what it costs

Buys: a main context that stays small and cached; a helper that can explore without polluting it; a clean division between planning and execution.

Costs: extra latency; duplicated work when the helper re-reads what the main already knew; a brief that must stand alone; and a report you should not trust without verification. In the test, the main agent re-ran the counts. That is the right habit.

Fails when: the task needs the main conversation's nuance; the helper's report drops a detail that mattered; or the helper loops without a step limit. Cap the steps, demand file paths, and verify the result.

What this build does not do

No journal for the helper; no parallel helpers; no per-helper model or budget; no durable restart. Each is a later step. The helper shares the same workspace and the same shell as the main agent, so isolation is in the context, not in the filesystem.

Retrieval check

What does the main agent receive from a helper?

Why: isolation is the point. If the trace came back, the main context would grow exactly as it would without a helper.

Why does delegation keep the main context small?

Why: the helper's eight calls and 21k tokens lived in the helper's message list. Only the report crossed back.

What must a delegation brief contain?

Why: the helper starts with an empty context. Anything it needs — file paths, definitions, success criteria — has to be in the brief.

What you can now do

  • Read a server log and compare helper tokens with main context size.
  • Write a self-contained brief for an agent that cannot see your conversation.
  • Say what delegation costs, and when not to use it.
