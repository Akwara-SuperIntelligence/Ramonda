Always-On Agents · Lesson 02

Write it down before you do it

The crash does not have to erase the step. It only has to erase the record. This lesson moves the record outside the process.

Time: 50 min Build: journal + reconcile Stack: Python 3.12 Map: durability

Lesson 01 ended with the disk and the execution state disagreeing. The file existed; the agent did not know. This lesson closes that gap enough to recover. The fix is not more saving. It is saving in a different order.

The one idea

Record the decision before the act. A line that says "I am about to call write_file with these arguments" turns a silent loss into a known unknown. The agent can then check instead of guess.

1. The order is the fix

In lesson 01, the harness saved the result after the tool ran. The crash window sits between those two events: the side effect is done, the result is not recorded. Saving more often does not close that window, because the window is inside the step.

Move a record to the other side of the act. Every call gets two journal entries: an intent before the tool runs, and a result after it finishes. The journal is append-only — one JSON object per line, never edited.

On restart the harness does three things. It loads the transcript. It reads the journal. For the last unfinished call it writes a synthetic tool result: INTERRUPTED — this call may have completed; check before you repeat it. The model then decides what to do with that knowledge.

The model never reads the journal. The harness reads it and puts one line into the conversation. That line is the model's only evidence that a call may have run.

Why save the call first? The transcript needs the assistant's tool call for the conversation to stay valid. The journal adds what the transcript cannot: whether that call actually started.

2. Build it

The build is lesson 01 plus about seventy lines, mostly the journal and the resume reconciliation. Read the diff before you run it — that diff is the lesson.

Build step · ~30 minutes

3 commands
  1. Diff the two harnesses and find the intent and result journal calls.
  2. Crash it on write_file, then read journal.jsonl.
  3. Resume and watch the agent check the file instead of rewriting it.
$diff -u build/lesson-01/agent.py build/lesson-02/agent.py | head -90

Then the same task as lesson 01, so you can compare the two failures directly:

$TASK="Create plan.md with exactly three bullets about launching a small agent. Then read it back and count them." $rm -rf build/lesson-02/state build/lesson-02/workspace $.venv/bin/python build/lesson-02/agent.py "$TASK" --crash-on write_file # exits 1, after the write, before the result is journaled $cat build/lesson-02/state/journal.jsonl $ls build/lesson-02/workspace

The journal has one line: an intent. No result. The file is on disk. That is the known unknown. Resume in the same terminal, so $TASK is still set:

$.venv/bin/python build/lesson-02/agent.py "$TASK" --resume

You should see the harness report the pending call, then the model inspect the workspace before it does anything else:

journal: 1 intents, 1 without a result
  pending: write_file {"path": "plan.md", ...}

[1] run_shell {"command": "ls -la; cat plan.md"}
    -> exit code: 0
       -rw-r--r--  plan.md
       ...three bullets...
[2] run_shell {"command": "grep -c '^- ' plan.md"}
    -> exit code: 0
       3

In lesson 01, the same crash left the agent blind: it either rewrote the file or rediscovered it by luck. Here the harness tells it that a call may have run, and the agent checks. The difference is not the model. It is the record.

Look at the journal, not the summary

The model's final paragraph can sound confident either way. The proof is in journal.jsonl and the tool calls: did it read before it wrote? Did the second run repeat the write? Judge the harness by the trace.

3. What this buys, and what it does not

It buys knowledge. After a crash, the harness can say one of three things about the interrupted call: it finished, it may have run, or it never started. The agent no longer guesses.

It does not buy exactly-once. If the side effect happened, it happened. The journal cannot undo it. "May have run" is the honest state, and the agent must verify or make the step safe to repeat.

That leaves a design rule for every tool: make it checkable (the agent can read the current state) or idempotent (a repeat causes no extra effect). A file write is usually both. An email is neither, so it needs an outbox with a sent-marker, or an approval step. The talk's rule is the same: ask before irreversible actions.

Real durable-execution systems do this journaling for you. Temporal records each step in an event history and replays it after a crash, which is why the talk can run an agent for days. The rule does not disappear: activities still have to tolerate a retry. The journal is the idea; the framework is the automation.

Retrieval check

What must be written before the tool runs?

Why: the intent is the only record that survives the crash window. A result written after the act is exactly what lesson 01 lost.

On resume, the journal has an intent but no result. What is true?

Why: the crash can land before or after the side effect. The journal cannot tell which. The agent must check the world, not assume.

Why is a journal not a guarantee of exactly-once?

Why: there is always an instant between the effect and the record. Only an idempotent or checkable step makes that instant safe.

What you can now do

  • Explain why saving after the act cannot close the crash window.
  • Read a journal and say whether a call finished, may have run, or never started.
  • Resume a crashed run without silently repeating work.
  • Say why a journal is not exactly-once, and what a tool must do about it.
